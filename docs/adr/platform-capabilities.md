## Obsidian note links and credentials

Store the logical vault alias and normalized vault-relative note path. On each device, map that alias to its local vault, retain the exact local vault name or ID returned by Obsidian, then build an `obsidian://open` link with separately percent-encoded `vault` and `file` values. Obsidian assigns each folder on a computer its own vault ID. A copied vault can therefore need a different local mapping. A note rename also needs to update the saved relative path or resolve a plugin-managed stable identifier. [Obsidian URI reference](https://obsidian.md/help/uri)

The plugin settings can hold the name selected through `SecretComponent`. At use time, `app.secretStorage.getSecret(name)` retrieves the named value or returns null. This is a store shared by plugins, so the Klaxon grant still needs narrow permissions and independent per-device revocation. Desktop 1.11.5 documents OS-backed encryption on disk. Android encryption at rest and actual revocation remain open. [Obsidian secret storage guide](https://docs.obsidian.md/plugins/guides/secret-storage) · [Desktop encryption change](https://obsidian.md/changelog/2026-01-20-desktop-v1.11.5/)

In Obsidian 1.12.7 on Windows, two vaults in the same disposable Obsidian profile used the same secret name independently. A replacement persisted after restart. Removing the entry through Settings → Keychain cleared it from that vault after restart and preserved the other vault’s value. A plugin can save the selected name in its settings and resolve it against the active vault. Removing this local entry still leaves issuer-side revocation to Klaxon. [Desktop rehearsal](../klaxon-v2-progress.md#obsidian-desktop-keychain) · [Public storage API](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Reference/TypeScript%20API/SecretStorage.md)

Windows Obsidian 1.12.7 opened the intended Markdown note via an explicit URI delivered to the app using its disposable profile. The fixture switched to a control note, opened the selected note, renamed it through Obsidian, switched away, and opened the renamed note with the updated relative path. The vault ID stayed the same. This supports manual path reconciliation. On Android 1.15.1, implicit `ACTION_VIEW` opened the correct same-path note across two app-storage vaults, including cold launch. The locator copied by Obsidian preserved a significant trailing space. A trimmed locator still dispatched but left the previous note visible. Android also reopened the renamed note after manually updating the path. Klaxon's launch path, Windows OS-wide dispatch, automatic rename tracking and revocation of a plugin grant at the issuer still need their own evidence. [Android rehearsal](../klaxon-v2-progress.md#obsidian-android-note-links) [Desktop rehearsal](../klaxon-v2-progress.md#obsidian-desktop-note-links)

**Android credential boundary.** In Obsidian 1.15.1 on one API 36 emulator, a second app-storage vault could read the first vault’s inert Keychain value and overwrite it. The first vault then showed the replacement. Treat the tested mobile Keychain as shared across vaults on that installation. Distinct names can prevent accidental collisions. They do not isolate credentials from other vaults. Keep manual note links available wherever separate vaults require separate trust. An authenticated plugin needs explicit workspace authorization, minimum scopes and independent revocation at Klaxon. [Mobile rehearsal](../klaxon-v2-progress.md#obsidian-android-keychain)

## Ordinary reminder delivery

Treat Web Push as best effort. Keep thin native scheduling in the Android design because the Chrome run produced no observed notification while locked or after unlock. The Windows local scheduler currently depends on the resident tray process. The route for a closed Windows client remains open. The server owns occurrences. Allocate one delivery route per device and occurrence, invalidate stale revisions, and provide overdue history and visible permission state. [Edge Web Push implementation](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/push) · [Windows scheduler](../../src-tauri/src/scheduler.rs)

For the one-time focused run on November 24, 2026, both push services returned HTTP 201. Will confirmed the matching worker receipt and one visible OS notification on each device, then reported removing both test subscriptions. Worker receipt and first-seen timestamps remain unrecorded. [One-time owner runbook](../p0-reminder-owner-test.md)

In the separate native Android run on November 25, Will saw the pre-armed reminder before unlocking. The fixture recorded a display request within the window and sampled the keyguard as unlocked at callback. That difference leaves locked-at-callback delivery inconclusive. [Physical Android evidence](../klaxon-v2-progress.md#android-native-visible-alarm-fixture)

**Windows after tray exit.** Keep OS-scheduled notifications as a candidate for reminders whose time is known while Klaxon is running. Windows build 26300 exposed the add, enumerate and remove methods, and retained a synthetic tag, group and UTC due time in memory. The existing NSIS app instead waits in its own process and calls the notification plugin at due time. Microsoft documents a five-minute delivery window for scheduled notifications, including a possible drop if the PC remains off. Keep overdue reminders available on reopening. [Windows scheduling guide](https://learn.microsoft.com/en-us/windows/uwp/design/shell/tiles-and-notifications/scheduled-toast) · [Klaxon scheduler](../../src-tauri/src/scheduler.rs) · [Immediate display](../../src-tauri/src/alerts/toast.rs)

OS scheduling under that identity remains unverified. Microsoft’s raw WinRT reference excludes desktop scheduling, while the Community Toolkit’s Win32 compatibility path can post a suppressed first notification to register an identity-less app. On a disposable Windows profile, verify that a queued occurrence survives process exit and that a fresh process can find and cancel that exact group/tag.
