# P0 architecture decision record

## P0-03 native session candidate

The [approved P0-03 backlog](../../KLAXON_V2_DESIGN_AND_IMPLEMENTATION_PLAN.md#9-implementation-backlog) calls for login, refresh and logout on both native targets. Before wiring a WebView to Convex, test whether a new native process can recover an owner-bound refresh marker and still require provider confirmation before granting access. The Windows candidate uses current-user DPAPI. The Android candidate uses an app-owned Android Keystore key to protect a record in private storage. Access tokens stay in memory. Both routes use OS facilities within the $0 additional budget. [Microsoft ProtectedData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata) · [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

Use only inert synthetic markers, a temporary store, two fixture owners and a simulated refresh response. Successful refresh may rotate the marker. A transport failure grants no access and permits retry. Expiry clears the record. Logout must survive relaunch, and one owner must never resume from the other owner's record. Keep marker values out of output and plaintext files. Record OS protection, cold-process behavior and provider simulation separately. The portable account client continues to require sign-in on reload.

**Hosted native session prerequisite, November 24.** The packaged command returns a status. The existing Convex HTTP and realtime clients require an access token, and the portable account client also holds the refresh token for rotation and sign-out. The packager restricts the synthetic session build to offline use. Connecting a hosted origin alone cannot establish an authenticated native session. [Account client](../../spikes/p0/portable/account.js) · [Packager](../../spikes/p0/native/package.mjs)

The Windows experiment exercises the option in which native code owns authenticated reads and subscriptions. The WebView receives projected task IDs and titles over Tauri IPC. Native drops the active subscription on sign-out, and the WebView discards replies that were already in transit when the session changed. A Windows process hosting a simulated provider exercises this boundary with no network or added service. [Packaged test and limits](../klaxon-v2-progress.md#packaged-windows-authenticated-task-read-and-subscription)

The production transport decision remains open. The leading candidate keeps refresh credentials in native storage and gives the supported Convex SDK a short-lived access token in WebView memory. The alternative keeps both tokens native and requires a native implementation of authenticated subscriptions, reconnect and refresh. Windows and Android have both exercised the SDK route through actual Tauri IPC and OS-protected storage. Each denied access during an outage and recovered from the sealed record. [Windows evidence](../klaxon-v2-progress.md#packaged-windows-dpapi-to-sdk-handoff) · [Android evidence](../klaxon-v2-progress.md#packaged-android-keystore-to-sdk-handoff)

The simulated provider can retire an access value immediately to check whether the SDK switches both its HTTP client and subscription. The pinned provider returns a replacement **refresh token** on a successful exchange. Native code must durably store that replacement before reporting success to the WebView. On a real local provider, revoking the packaged Windows session invalidated its cached bearer for reads and emptied its uninterrupted subscription while another login for the same owner stayed usable. During a subscription outage, the previously rendered task stayed visible until the same client reconnected and received an empty update. Treat cached reads as stale while disconnected, as the plan requires. Packaged Android against a real provider and hosted acceptance remain open. [Reconnect evidence](../klaxon-v2-progress.md#windows-subscription-reconnect-after-revocation) [Windows provider evidence](../klaxon-v2-progress.md#packaged-windows-revocation-on-a-real-local-provider) [Account client](../../spikes/p0/portable/account.js) · [Offline SDK comparison](../klaxon-v2-progress.md#offline-convex-sdk-owner-switch)

Convex Auth 2.1.0 lets a client retry the presented refresh token until its successor is first used. The native client therefore needs a single writer per session. Before publishing a replacement it must keep the preceding record recoverable. After publication a new process must recover the successor, even if the WebView never received an acknowledgment. A valid `noSession` response ends the session. A malformed response or transport failure must preserve the protected record for retry. The packaged fixture can test these storage boundaries using synthetic responses. Hosted acceptance must separately check the real provider’s retry and revocation behavior. [Pinned package](../../spikes/p0/package.json) · [Windows fixture procedure](../../spikes/p0/native/README.md#packaged-windows-sdk-handoff)

The Android fixture uses a single packaged app process, serialized plugin calls, a non-exportable Keystore key and an encrypted `AtomicFile` in app-private storage. Android can log a failed rename and return from `finishWrite`. The client therefore compares the published ciphertext with the staged bytes before issuing access. A new process still has to obtain provider confirmation. [Android fixture procedure](../../spikes/p0/native/README.md#packaged-android-sdk-handoff)

On Android, initial sign-in can die after key creation but before the encrypted record is published. Under the fixture's single-writer assumption, resume or a fresh validated sign-in may discard that slot's staging file and key only when both the published record and its legacy backup are verifiably absent. A backup blocks cleanup even when the base file is missing. The [initial sign-in evidence](../klaxon-v2-progress.md#android-initial-sign-in-to-keystore) covers these two recovery paths.

The [Windows](../klaxon-v2-progress.md#windows-sign-out-after-a-lost-acknowledgment) and [Android](../klaxon-v2-progress.md#android-sign-out-after-a-lost-acknowledgment) fixtures distinguish an issuer that may have committed revocation from a client that received confirmation. Keep the protected refresh record available for an idempotent retry while denying fresh access. Persist a confirmed acknowledgment before deleting that record so local cleanup can resume after process termination. Both fixtures validate the same Convex response in Rust. A separately built Windows fixture now sends the native sign-out mutation over IPv4 loopback. Once it records the pending journal it can release the in-memory provider mutex, so concurrent SDK access sees the revoked owner while the file lock still protects the ciphertext. Hosted auth and realtime behavior remain open. [Packaged HTTP evidence](../klaxon-v2-progress.md#packaged-windows-sign-out-over-loopback-http)

The opt-in Windows build also exercises cold refresh over native HTTP. The fixture gives transport status precedence over the body, commits a valid successor to DPAPI before granting access, and requires confirmed expiry before clearing the slot. The sealed Windows record binds each grant to a session identifier that survives rotation and changes at fresh sign-in. A surviving native provider checks that identifier on its next access. Hosted sessions and subscriptions still need issuer-level verification. [Cold refresh evidence](../klaxon-v2-progress.md#packaged-windows-cold-refresh-over-loopback-http) · [Replacement evidence](../klaxon-v2-progress.md#windows-session-replacement-for-the-same-owner)

## Shared client and backend

Accepted for the spike on 2026-11-23. Retain the existing shared static Svelte/Vite build. Keep native OS services behind Tauri commands. Place the spike in its own package so its dependency graph and generated configuration cannot enter a v1 release. Use a mount-relative task fragment (`#/tasks/<encoded-id>`) as the P1 routing candidate. The static host can serve the entry document on direct navigation and reload without a rewrite. Windows Tauri also served a history-style path through its asset fallback. P1 still needs to resolve the ID within the active account and open the task detail. [Routing probe](../klaxon-v2-progress.md#task-links-on-static-and-tauri-origins)

Convex owns online state. An owner-indexed subscription to a bounded task list is the first slice. Resolve the owner from the verified session inside each backend function. Start with Convex Auth; retain this choice only after real login, refresh, logout and reconnect work in Svelte, WebView2 and Android WebView. Capture callback and secure storage behavior on each. A successful local server test cannot prove availability with the desktop powered off.

Keep deterministic integration reconciliation and reminder scheduling in the backend. Give agents scoped, versioned HTTP/MCP access to the same validated domain functions. Select native vs web notification delivery from actual background and closed-app evidence. A provider acknowledgement alone cannot establish that a person received a reminder.

Will's [owner-reported physical smoke](../klaxon-v2-progress.md#remaining-p0-tests) supports keeping Convex for the hosted task spike. Android saved a rename while Windows was powered off, and Windows read it back after restart. Android signed in again after reopening. The native credential-storage decision and the notification delivery decision remain provisional.

Keep v1 authoritative during rehearsal. Use synthetic archives and a disposable workspace. Cross-device reconciliation, restore and explicit owner acceptance precede a change of authority. Running both schedulers on real data would make delivery results ambiguous.

The loopback probe permits synthetic password registration and keeps tokens in memory. Before a hosted test, restrict enrollment to disposable test identities, use HTTPS and confirm the team is Free. The P1 auth decision depends on reload, expiry, concurrent refresh and revocation in actual clients. Keeping the same UI code does not make browser storage or native callbacks equivalent.
